00What this project is

ReeferReady PMS is a container readiness pipeline for a reefer depot network: ten repair stages from gate-in to release, a checklist that varies by container type, and one view of what's delayed across four depots. Four roles are modeled — manager, supervisor, technician, viewer — and the whole visual layer sits on a hand-authored, code-generated “Crystal” design system.

Stack: an npm-workspaces monorepo with no Turborepo/Nx — orchestration is plain npm -w flags plus concurrently.

packages/sharedDependency-free domain core (readiness rules + zod schemas), consumed as raw TypeScript by both sides.
apps/apiFastify 5 + Prisma 6 + SQLite backend, JWT auth, audit trail.
apps/webReact 19 + Vite frontend: TanStack Query/Table, Radix UI, cmdk, TipTap, bound to the generated Crystal CSS/icons.
tools/extract-design-system.mjsThe code-generation bridge from the design-system source HTML into the app's CSS/icons.

The repo's stated organizing principle, from its own README, is that “no value is ever typed twice.” That claim holds completely for design tokens and mostly holds for domain logic — the read found several concrete places where it's violated in practice (see §10).

01Core features & workflow

What the app actually does for its four kinds of users, and the pipeline every container moves through from arrival to release.

Core features

  • Ten-stage readiness pipeline — every container moves through gate-in, structural & IICL repair, T-floor repair, mechanical, electrical, sandblast & paint, logo/stencil & decals, cleaning, PTI, and final QC, each with a fixed day budget.
  • Type-aware checklists — standard, double-compressor, and anteroom (internal/external mantrap) containers each get a checklist scoped to their variant, snapshotted at registration so later template edits never rewrite completed work.
  • Live readiness gauge — every container's overall completion is drawn as the container itself (a filled outline with corrugation ribs at real stage boundaries), not a generic progress bar.
  • Delayed / at-risk tracking — any container past its stage's day budget surfaces automatically on the Delayed screen and dashboard stat cards, computed from one shared definition of “late.”
  • Kanban pipeline board — all containers laid out by current stage across a horizontally-scrolling ten-column board.
  • Depot Command — the manager's home screen: the home depot's own fleet, a read-only view of the rest of the network, inbound off-lease units, and customer orders matched against available inventory.
  • Tomorrow's Work queue — every outstanding checklist task across the fleet, flattened one row per task, with the assigned technician, their backup, and the fleet-average hours for that task.
  • Order-to-inventory matching — customer orders are automatically matched to the best-progressed available container at the home depot, with cross-depot transfer suggestions when nothing local qualifies.
  • Container detail drawer — a side panel for any container: its per-stage checklist, a stage-advance action (with a confirmation dialog if tasks are still open), a rich-text handover note, and the full event history.
  • Role-based permissions — four roles (manager, supervisor, technician, viewer) gate who can register, edit, advance, tick tasks, or delete a container.
  • Command palette (⌘K / Ctrl+K) — jump to any screen or container, or run a quick action, from anywhere in the app.
  • Full audit trail — every registration, task completion, stage advance, and edit is logged as a timestamped event against the container.
  • Checklist template library — a standalone reference screen showing every stage's tasks and per-variant day budgets, independent of any single container.
  • Light/dark theming — follows the OS preference until the user picks explicitly; zero hand-written dark-mode CSS, entirely token-driven.

Container lifecycle workflow

  1. Gate-in & registration. A manager or supervisor registers the container — unit number, size, type, customer, depot, assignee. Its checklist is generated from the template library for its exact type/variant and snapshotted onto it; the pipeline stage is set to gatein.
  2. Stage work. Technicians tick checklist items as work is completed in the current stage; each tick is timestamped, attributed, and logged as an audit event.
  3. Stage advance. Once a stage's checklist is complete, a supervisor or manager advances the container to the next stage. If tasks are still open, the UI blocks with a confirmation naming exactly which tasks remain — advancing anyway is a deliberate, explicit override, never a silent skip.
  4. Delay detection. Every stage carries a day budget (extended by a day for double-compressor units in mechanical, and for anteroom units in electrical). A container that overruns its budget is automatically flagged delayed everywhere it appears — dashboard, board, drawer — from one shared definition.
  5. Final QC & release. Once the QC stage's checklist reaches 100%, the container is “ready for release.” A container sitting in QC is never counted as delayed, however long it waits for its gate pass.
  6. Order fulfilment. In parallel, open customer orders are matched against available containers (or flagged for cross-depot transfer) so a ready unit is routed to the order that needs it.
  7. Removal. Only a manager can remove a container from the system entirely — a destructive, explicitly confirmed action that also removes its task and event history.

02Architecture, traced through one real request

A user ticks a checklist item in ContainerDrawer.tsx. Here is exactly what happens, read directly out of the code:

  1. useToggleTask (lib/queries.ts L56–63) fires api.toggleTask(id, key, done).
  2. lib/api.ts's request() (L66–96) attaches the bearer token, POSTs /api/containers/:id/tasks, and turns any non-2xx response into a typed RequestError carrying status/code/fields/payload.
  3. Server-side, routes/containers.ts runs the request through authenticate (a global preHandler hook, L27) then requirePermission('container:task'), both from auth.ts.
  4. The handler (L269–307) runs a prisma.$transaction([...]) that flips the task's done/doneAt/doneBy and inserts a ContainerEvent audit row atomically — the audit line can never desync from the mutation it describes.
  5. The container is re-fetched via containerInclude + toContainer() (mappers.ts) and returned with the server's own today (today.ts).
  6. The client patches/invalidates the TanStack Query cache; every screen watching useOverview()/useContainer() re-renders.
The load-bearing decision: packages/shared is not just shared types — it's the only place business rules are computed. containers.ts imports isLate, isReady, nextStage, checklistFor, stageBudget directly rather than reimplementing them, and even filters “late/ready” in application code instead of SQL specifically so there is exactly one definition. The web side calls the identical functions to render status pills, progress and the work queue. That's what makes “API and UI can never disagree” structurally true rather than aspirational.

03packages/shared — the domain core

index.ts4-line barrel — export * from the three modules below. Zero logic.
process.tsStatic business data: 10 fixed stages + day budgets, the ~48–51-item task-template library per container type (checklistFor), variant extra-day rules, plan totals. No imports — the leaf of the dependency graph.
readiness.tsPure derivations: progress %, isLate/isReady, the Status (tone+icon+label+detail) object that structurally enforces “never colour alone,” the prioritized work queue, and greedy order-to-inventory matching. today is always passed in, never read from the clock.
readiness.test.tsBehavior-pinning Vitest suite (“how it looks changes, what it does does not”) — no mocks, exercises real stage/task data.
schemas.tszod contracts built from process.ts's own enums, so API validation and web form types can't drift apart.

Findings

  • bugcontainerId doesn't validate what its own comment says it does (schemas.ts L26–31): the comment describes real ISO 6346 format (4 letters + 7 digits) and claims it “normalises rather than rejects” — the actual rule is only trim + 4–20 char length bound + whitespace collapse. No regex, no check-digit. "AAAA" would pass straight through.
  • Calendar dates are never actually validated — isoDate and parseISODate only check the YYYY-MM-DD shape. 2026-02-30 silently rolls over to March via native Date normalization instead of being rejected anywhere in the shared package.
  • totalPlanDaysFor in readiness.ts reimplements totalPlanDays from process.ts instead of calling it — duplication inside the one package whose entire job is to prevent duplication.
  • Latent key-collision risk: task-template keys (e.g. mechanical.07) are positional, generated from array index, documented as “stable” — true only for in-place renames. Inserting or reordering a task mid-array would silently reassign every later task's key in that stage, and since averageHoursFor() aggregates fleet-wide by key, old and new containers could end up sharing a key that means two different things — a silent, fleet-wide data corruption with nothing enforcing “append-only” and no test guarding it.

04apps/api — the backend

Core plumbing

app.tsComposition root: registers CORS/rate-limit/JWT, a global error handler (Zod→422, 4xx pass-through, 5xx always generic), a uniform 404, health check, and the four route plugins.
auth.tsSecurity core: scrypt password hashing (timing-safe compare, no native deps), the role/permission table (flagged in its own comment as “NEEDS SIGN-OFF”), and the two Fastify preHandlers authenticate/requirePermission.
db.tsSingle shared PrismaClient singleton.
env.tszod-validates all env vars at import time; re-applies pre-existing process.env values after loading .env, so a stray file can never silently override the test runner's forced database.
http.tszodToApiError, parseOr422, notFound/conflict — the one error-shape vocabulary every route uses.
mappers.tsTranslates Prisma rows into shared DTOs; atLocalMidnight() avoids the classic UTC-shift date bug.
server.tsEntry point — builds the app, listens on 0.0.0.0:PORT, graceful shutdown on SIGINT/SIGTERM.
today.tsResolves “today” per-request; honors a client-supplied x-today header outside production only — the deterministic-time seam the test suite depends on.
  • A placeholder JWT_SECRET is long enough to pass validation (44 chars vs. a 16-char minimum) — a deployment that copies .env.example without changing it boots successfully on a publicly-known signing secret.
  • mappers.ts does JSON.parse(t.onlyFor) with no try/catch — a malformed column would 500 the entire container fetch.
  • mappers.ts casts DB strings straight to shared union types via plain as — no runtime check.
  • today.ts's escape hatch is gated on “not production,” not specifically “test” — any non-prod deployment would accept a caller-spoofed “today.”
  • No process-level unhandledRejection/uncaughtException handler in server.ts.

Routes and integration tests

routes/auth.tsLogin (10/min rate-limited) and “who am I.”
routes/containers.tsThe workhorse — list/search, read-with-audit-trail, register (snapshots the checklist so template edits never rewrite completed work), edit, tick-task (transactional), advance-stage (force-past-open-tasks contract), delete, checklist-library.
routes/overview.tsOne big server-computed aggregate feeding Dashboard + Depot Command.
routes/reference.tsRead-only form metadata — depots, active technicians, vocab.
__tests__/api.test.tsThe whole integration suite — real seeded SQLite via .inject(), no mocks.

Real bugs found

  • bugLogin's anti-enumeration is broken by a timing side-channel. routes/auth.ts L21: const ok = user ? verifyPassword(...) : false — the deliberately-slow scrypt check only runs when a matching user row exists. A non-existent email short-circuits instantly with no hashing, so response latency leaks whether an email is registered — directly contradicting the route's own “roughly the same work either way” comment. The enumeration test only checks the response message, not timing.
  • bugDeleting a container deletes its own audit trail. DELETE /api/containers/:id cascades ContainerEvent rows away with the container. The only surviving record is a request.log.warn line, not a queryable one — for a product whose headline feature is an audit trail, deletion is the one action it doesn't actually retain.
  • overview.ts's docstring justifies server-side aggregation as “the phone doesn't download the whole fleet,” but the response still embeds the complete containers array with full checklists — the client downloads full detail twice.
  • overview.ts/reference.ts do unpaginated, unfiltered findMany across every table on every request, with no depot-scoping despite SessionUser.depotId existing on the JWT.
  • api.test.ts never signs in or tests the supervisor role at all — only manager, technician, viewer. Supervisor has zero test coverage.
  • The “working a container”/“permissions” test blocks are stateful and order-dependent, mutating the same container across it blocks rather than isolated fixtures.

Database schema and seed data

prisma/schema.prismaEight models: User, Depot, Technician, Container (PK = the real ISO 6346 unit number), ContainerTask (snapshotted per-container), ContainerEvent (audit trail), OffLeaseUnit, CustomerOrder. Thoughtful onDelete variety across relations.
prisma/seed.tsDeliberately hand-authored, deterministic fixture — 4 depots, 8 technicians in 4 buddy pairs, 4 users (one per role), 10 containers positioned to exercise every dashboard state.
  • No native Prisma enums anywhere — role, container type, stage, priority, event kind, grade are all plain String columns; validity is a comment-only convention, not a DB constraint.
  • “Append-only” audit trail is a documentation convention only — nothing in the schema (trigger, restricted grant, immutability) actually prevents an UPDATE/DELETE on ContainerEvent.
  • Audit fields are free text, not foreign keys — ContainerTask.doneBy and ContainerEvent.actor are plain strings.
  • Depot.isHome's “exactly one home depot” invariant is documented, not enforced.
  • No prisma/migrations directory exists — the workflow is db push, not versioned migrations, undercutting the schema's own claim that a Postgres move later is “a provider swap plus a migration.”
  • seed.ts hardcodes its own stage order instead of importing it from packages/shared — a literal duplication of the one thing the project says is defined exactly once.

05apps/web — the frontend

Core and lib — the composition root

App.tsxTop-level route table + auth gate; hardcodes 8 route paths independently of lib/nav.ts.
main.tsxProvider stack: StrictMode→Theme→QueryClient→Auth→Tooltip→Toast→Router→App. Thoughtful retry policy — never retry 4xx, retry transport failures up to 2×.
lib/api.tsThe one HTTP client; typed RequestError; localStorage token store with graceful in-memory fallback.
lib/auth.tsxSession context; client-side permission table explicitly commented as a UX-only mirror of the server.
lib/queries.tsTanStack Query hook layer over every api.* call; every mutation invalidates overview.
lib/format.tsCentralized date/duration formatting.
lib/nav.tsThe one declarative nav structure — sidebar/palette/headers all read it.
  • bugformatDateTime violates its own module's stated invariant. format.ts's doc-comment says dates must render identically regardless of viewer timezone; formatDate/formatDateShort honor that, but formatDateTime uses new Date(iso) + .getHours()/.getMinutes() — both browser-local — so an audit-trail event's displayed time differs between two users in different timezones viewing the same event.
  • App.tsx's route table and lib/nav.ts's config independently hardcode the same 8 paths — currently in sync, nothing enforces it stays that way.
  • No mutation hook in lib/queries.ts defines an onError handler at the hook level — error surfacing is left entirely to call sites.

Components — app-level and the Crystal design system

App-level (components/app): AddContainerDialog, AppShell (sidebar rail/nav sheet/app bar), CommandPalette (⌘K, cmdk-based), ContainerDrawer (the heaviest integration file — checklist, advance, notes, history, removal, opened via a ?container=<id> URL contract), ContainerGauge (readiness drawn as the container itself), KanbanBoard (the ten-stage board).

Crystal primitives (components/crystal): Button, Data (status pills structurally forced to carry tone+icon+label), DataTable (TanStack Table + a responsive cards fallback driven by column metadata), Feedback (alerts/toasts/AsyncRegion), Form, Icon, Overlay (Radix-backed modal/drawer/menu), RichText (TipTap-based handover-note editor).

Two real bugs found here

  • bugOverlay.tsx L39 — dead ternary. aria-describedby={description ? undefined : undefined}. Both branches evaluate to undefined. Harmless today since no caller passes description, but if one ever did, this would silently suppress Radix's own automatic aria-describedby wiring.
  • bugRichText.tsx L179–182 — premature “saved” state. The Save button calls setDirty(false) immediately after invoking onSave(...), without waiting for the async mutation to succeed. If the save fails, the editor's “· unsaved” indicator and Save button have already cleared — the UI silently reads as saved even though nothing persisted.

Other findings: AddContainerDialog always defaults the new technician to technicians[0], biasing every registration toward one person; DataTable opens a row via the first visible cell, not necessarily the column flagged lead in its own metadata contract; AsyncRegion renders raw error.message directly to end users of any role.

06The design-system pipeline

The chain: source/crystal-design-system.html (4,191 lines, the only place tokens/CSS/icons may be authored) → tools/extract-design-system.mjs → four gitignored generated files → the running app. app.css is the only hand-authored CSS file, mechanically policed by stylelint so no literal colour can bypass the token pipeline.

Two genuine bugs, found by comparing source HTML against generated output

  • bugA duplicated “CONTAINER GAUGE” section silently loses its first definition. The source HTML declares this banner section twice, with two incompatible implementations. The extractor builds its lookup as new Map(sections.map(s => [s.name, s.css])) — a plain JS Map, so the later duplicate silently wins with no warning. Verified directly: crystal.css contains only the second definition; the generated manifest's unfiltered section list is the only artifact that reveals the name appears twice.
  • bugThe reduce-motion cherry-pick can never match, by a comma-splitting bug. The extractor's allow-list stores the manual reduce-motion escape hatch as one three-selector, comma-joined string; the matcher splits the rule's own selector list on commas and checks each piece against the whole joined string — which can never be equal. Verified two ways: crystal.css contains zero .reduce-motion selectors, and the manifest's own “dropped” list names the exact rule that also appears in the allow-list, in the same file.
  • Icon dedup uses the opposite tie-break rule from CSS-section dedup — icons keep the first occurrence of a duplicate id, sections keep the last. Same file, two contradictory silent policies for the same class of authoring mistake.
  • An unsigned-off contrast correction has been live for 5+ weeks: tokens.css's source carries a “CONTRAST CORRECTION — 2026-08-11, awaiting sign-off” comment describing seven token-lightness changes, with no ticket reference anywhere in the repo.

07End-to-end test suite

Playwright runs fully serial against a real running API+web stack, reseeded once before the run. Auth is handled once by a dedicated setup project; five spec files cover functional/RBAC behavior, axe-core accessibility across 8 screens × 2 themes, responsive layout, design-system contract assertions (including a genuinely rigorous SVG-geometry check on the readiness gauge), and pure visual capture.

  • Several tests hardcode literal computed RGB values tied to design tokens instead of comparing self-referentially — any deliberate, correct palette change will fail these for cosmetic reasons.
  • The “phone” responsive spec sets its own viewport with no project restriction, so it silently runs twice per full suite — once under desktop, once under phone — doubling its runtime for no added coverage.
  • A manual fixture-restoration pattern (toggle a checkbox, then toggle it back at the end) is fragile: if the test fails partway through, the “undo” never runs and the shared fixture stays dirtied for every subsequent test.
  • The screenshot-capture spec contains zero expect calls — it always “passes” regardless of what the images show.

08Tooling and workspace config

An unusually strict shared TypeScript baseline (noUncheckedIndexedAccess, verbatimModuleSyntax, hard-error unused locals/params, consistent-casing enforcement) and a flat ESLint config with project-specific Radix-aware accessibility tweaks.

  • Possible build-path mismatch: apps/api/tsconfig.json sets rootDir: "." while including both src/** and prisma/**, which should make tsc -b emit dist/src/server.js — but the package's start script runs node dist/server.js. Not empirically confirmed in this environment; worth verifying with a real build.
  • packages/shared/package.json's exports point directly at ./src/index.ts, not dist/ — the package's own build output isn't actually consumed by any resolution path.
  • ESLint globally ignores apps/api/prisma/**, so seed.ts — a file that ships and executes in production — is exempt from the zero-warning lint gate everything else is held to.
  • No Prettier or other formatter config anywhere — style consistency relies entirely on ESLint/stylelint.

09Auth & permissions model

Four roles, six permissions. Compared directly, the server table (auth.ts) and client table (lib/auth.tsx) are currently identical — manager gets all six, supervisor everything but delete, technician read+task, viewer read-only — but they're two independently hand-maintained copies with no shared source enforcing sync. A server-side policy change requires remembering to hand-edit the client too, and nothing would fail a build if it drifted.

Enforcement is clean on the server (composable preHandlers on every mutating route) and explicitly UX-only on the client, per its own comment: “the server is still the authority.”

Notably, supervisor is a fully-specified role with zero coverage anywhere — not in the API test suite's setup, not in the login screen's demo credentials, not in the Playwright auth setup, which signs in only as manager. It's the one role nobody, test or human, ever actually exercises.

11Overall code-quality assessment

What's strong

Unusually self-aware — nearly every file justifies a non-obvious choice inline. The packages/shared boundary is genuinely disciplined: readiness.ts is 100% pure, today-threaded functions, and routes never reimplement a calculation they could import. The TypeScript baseline is strict well beyond typical projects this size. The design-system extractor, despite its two bugs, is well-engineered — content-hash stamping, a real CSS-aware nested-at-rule splitter, fail-fast guards. Accessibility is structural, not aspirational: status objects that can't be colour-only, required tooltip labels, correct ARIA roles on destructive confirms.

What's weak

The recurring pattern is documented intent the code doesn't fully deliver on — not sloppiness, but comments written to the intended design that the implementation later diverged from. Test coverage has specific, real gaps rather than being broadly thin — no supervisor coverage anywhere, a stateful integration test file, a screenshot spec that always passes. Security posture stacks several unenforced trust boundaries on the same login path. Architecturally, the several “single source of truth” violations found have zero build-time or test-time protection against drifting apart — precisely the failure mode the rest of the architecture was built to prevent everywhere else.

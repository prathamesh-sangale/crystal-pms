08

Layering

z-index scale

Seven fixed layers. No component invents its own z-index; if two things collide, one of them is on the wrong layer.

Scale
0Page content, cards, tables
100Sticky header, sticky table head
400Dropdown, popover, autocomplete
700Drawer, bottom sheet
800Modal + scrim, command palette
900Toast
1000Tooltip — always on top
Rules
One scrim at a time

A modal opened from a drawer replaces the drawer. Two stacked scrims are a bug, not a pattern.

Tooltips outrank modals

A tooltip inside a modal must still render above it — that's why tooltip is the only layer above 900.

Toasts survive navigation

Toast lives at page root, not inside the view that fired it, so a route change never kills the confirmation.

Do / Don't

the guardrails

Everything above can be followed to the letter and still produce a screen that feels off-system. These are the failures that actually happen.

Do
  • Keep one navy hero block per screen and let everything else stay white.
  • Use amber for the single thing you want read first — a CTA, an active nav item, one chart bar.
  • Pair every status colour with a word, so the meaning survives greyscale.
  • Give white cards a 1px border; give tinted cards none.
  • Use mono for machine values and Inter for language.
  • Disable a control at its limit rather than letting a click do nothing.
  • Mirror the real layout in the skeleton so nothing jumps on load.
  • Say what an empty state will contain and give one button that fills it.
Don't
  • Introduce a fifth colour for an icon chip, a chart segment or a secondary button.
  • Fill the sidebar with solid navy — the active item takes a tint, not a block.
  • Put white text on amber, ever. Amber takes black.
  • Use semantic red or green as a button colour; they belong to status only.
  • Stack two hero cards and make the eye choose.
  • Add gradients, glassmorphism, neon or drop-shadowed text.
  • Let a toast carry a decision — if it needs an answer, it's a modal.
  • Invent a z-index. Seven layers exist; use one of them.

Headless Bindings

for apps built on behaviour primitives

Everything above was written for class toggling, which is how this page works. A product built on unstyled behaviour primitives — for focus traps, keyboard handling and ARIA it should not be reimplementing — signals state with a data-state attribute instead, and positions floating layers itself. These rules let the same classes serve both, so there is never a second visual definition of a menu or a drawer.

ClassBound behaviour
.dd-menu .pop-panel .ms-panel .ac-panelDrops the design system's own offsets when something else is positioning the layer; keeps every visual property

Rules
The classes stay the source of truth

A binding may neutralise a position or add an animation. It may never change a colour, a size, a radius or a weight — if it does, two definitions of the component now exist.

Tooltip arrows

The CSS arrow on .bubble is switched off when a primitive positions the bubble, because the arrow has to follow the side it lands on. Use the primitive's own arrow with .tip-arrow.

Rule · a component gets bindings, not a second stylesheet. If a primitive cannot be made to wear these classes, that is an argument against the primitive, not for a new set of classes.

## 2. Scope & Requirements

**What it does today (code-verified):**
- **v1 (backend, still live at the HTTP layer; UI deleted from the working tree):** registers a reefer container into a fixed 10-stage pipeline (`gatein → structural → tfloor → mechanical → electrical → paint → logo → clean → pti → qc`), tracks a per-stage checklist snapshotted from a task-template library (varies by container type: `standard`/`double`/`anteroom`), computes lateness against a per-stage day budget, gates stage advancement behind open tasks (overridable with `force`), keeps an append-only audit trail (`ContainerEvent`), and serves a depot-network overview (order-to-inventory matching, off-lease incoming units, per-depot stats). Four JWT-authenticated roles (manager/supervisor/technician/viewer) with a server-side permission table. Source: `packages/shared/src/process.ts`, `readiness.ts`, `apps/api/src/routes/*.ts`, `apps/api/prisma/schema.prisma`.
- **v2 (UI, mock data only):** per `SPEC.md`, replaces the fixed-stage model with Survey (pre-gate-in inspection) → Gate-In → parallel Sections (Painting, PTI, Repairment, Cleaning) → Ready to Move, a start/stop timer per task instead of a checkbox, a single Admin user model (Owner read-only role designed for but not built), Worker records (not accounts) of 7 types, a separate Movement Log (load/offload/shift) tied to task site requirements, aging/SLA badges, a priority/rush flag, draft intake saves, and printable per-container and yard-wide reports. All of this is implemented in `apps/web/src/screens/v2/*` and `apps/web/src/components/v2/*`, running entirely on `apps/web/src/lib/v2Store.tsx` + `mockV2.ts`.
- **Explicitly out of scope (per `SPEC.md` hard constraints):** changing the visual design system (`source/crystal-design-system.html`, `tokens.css`, `crystal.css`, generated icons) — stated as a hard constraint at the top of `SPEC.md` and repeated in §9 "Never". Multi-depot support was explicitly dropped for v2 (§8 item 6: "This build is for one yard, not a network of depots").
- **Scope drift detected:**
  - The v1→v2 UI cutover is itself a large, deliberate scope change from "role/pipeline model" to "Admin+Workers/Survey+Sections model" — documented, not accidental, but it means the originally-shipped v1 UI (and its matching, tested backend) is now unreachable from the app's own navigation.
  - The backend was never part of the v1→v2 UI scope ("Left alone, on purpose" — SPEC.md item 10) — so the UI scope changed while the backend scope stayed frozen, producing the UI/backend mismatch described above. This is drift in the sense that the product description ("a real backend-driven pipeline tool") and the shipped UI experience ("a mock-data preview") have diverged, even though each individual change was intentional.

## 5. Technical Decisions & Trade-offs

Primary source: `SPEC.md`'s dated "Resolved" log, cross-checked against code.

- **SQLite for v1, by design, not by accident.** `schema.prisma`'s header comment states the choice explicitly: "SQLite so the whole stack runs from `npm run setup` with no infrastructure... moving to Postgres is a provider swap plus a migration — no model changes." This reasoning is also why the Supabase migration (Postgres) was a plausible next step rather than a rewrite.
- **Single source of truth for domain logic (`packages/shared`).** Both `isLate`/`isReady` (v1) and the (unbuilt) v2 section-completion gate are specified to live here so "the API and UI can't disagree" (`SPEC.md` §4.4, and `readiness.ts`'s own header comment). Trade-off: this discipline was kept for v1, but the v2 mock store currently duplicates its own gating logic inside `v2Store.tsx`/`mockV2.ts` rather than in `packages/shared`, since there is no v2 backend yet to share it with — a known, temporary exception.
- **Timer-based task completion over checkboxes (v2).** `SPEC.md` §2: "a start/stop timer per task... stopping it *is* what marks the task done." Rationale given: tracks actual labor time, not just a binary signal — feeds the hours-worked and turnaround dashboards (item 25).
- **Single Admin role replacing 4-role RBAC (v2), but RBAC machinery kept, not deleted.** `SPEC.md` §9 "Ask first — before deleting the JWT/RBAC scaffolding... reuse and collapse it... since Owner is a likely near-term addition." This explains why `apps/api/src/auth.ts`'s 4-role permission table is untouched even though v2 only needs Admin today.
- **Worker records, not accounts.** Rationale (`SPEC.md` §1): painters/technicians/etc. never log in; only the Admin does. Simplifies auth surface for the new model considerably versus v1's one-login-per-role design.
- **Movement log coupled to task site, not a free-standing form.** Resolved 2026-09-30 (§4.3b): every task implies a site, so starting a task whose site differs from the container's current site requires an explicit "Move to `<site>`" step first — chosen so the log can't silently drift from physical reality, while Load/Offload remain manual because they are genuine external events.
- **Service-role-only Supabase access, RLS enabled with no policies.** `supabase.ts`'s own comment: defense-in-depth — even if the anon key leaked, RLS with zero permissive policies means it can read/write nothing. Chosen because `apps/api` is designed as the sole Supabase caller.
- **Plain `users` table in the Supabase migration instead of Supabase Auth.** Explicit rationale in the migration file: keeps `apps/api/src/auth.ts`'s existing custom-JWT/scrypt login code working unchanged; defers an Auth-vs-custom decision.
- **Library choices, as evidenced by `package.json`:** Fastify 5 + `@fastify/*` ecosystem (JWT, CORS, rate-limit, sensible) for the API; Prisma 6 for the ORM; Zod for schema validation shared between client and server; Radix UI for accessible unstyled primitives (paired with the generated Crystal CSS classes); TanStack Query/Table; TipTap for rich text; cmdk for the command palette; Playwright + axe-core for e2e/accessibility testing; Vitest for unit tests; stylelint + ESLint (flat config, typescript-eslint, jsx-a11y, react-hooks) for static checks. No evidence of alternatives having been trialed and rejected in-repo — `[UNCONFIRMED: no ADRs or comparison notes found]`.

## 8. Risks & Open Issues

**Security:**
- `JWT_SECRET` is validated server-side (`env.ts`: Zod `.min(16)`), and `.env.example` ships an obviously-fake placeholder (`"dev-only-secret-change-me-in-any-real-deployment"`) with a prominent comment ("Change this.") — reasonable hygiene for a dev default, but there is **no deployment pipeline or process yet that would force this rotation** (see §9), so the only safeguard against shipping the dev secret is human discipline plus the README's one-line warning ("Change `JWT_SECRET` before this is deployed anywhere").
- Passwords are hashed with `scrypt` (Node's `node:crypto`, no native deps) and compared with `timingSafeEqual` — a sound, deliberate choice (`auth.ts` comments explain the no-native-module rationale).
- Login responses are deliberately timing/shape-uniform whether the account exists or the password is wrong (`routes/auth.ts` comment) — a correct anti-enumeration measure.
- Rate limiting: global default 300 req/min (`app.ts`), tightened to 10/min specifically on `/api/auth/login` (`routes/auth.ts`) — reasonable baseline, though `[UNCONFIRMED: whether 300/min global is appropriate for a production deployment — no load-testing evidence found]`.
- CORS: origin restricted to `env.WEB_ORIGIN` (comma-split list), credentials allowed, headers allow-listed to `content-type, authorization, x-today` — scoped reasonably, but `WEB_ORIGIN` defaults to `http://localhost:5173` if unset, so a misconfigured production deploy would default to an unreachable-in-prod but not fail-closed value. `[UNCONFIRMED: no explicit production CORS config example provided anywhere]`.
- The seeded dev accounts all share one password (`readiness`) across all four roles — acceptable for a seed fixture, dangerous if ever reused as real production credentials; nothing in the repo prevents that reuse besides the README's instruction to change `JWT_SECRET` (which does not itself invalidate seeded user rows).
- Supabase service-role key handling is sound in design (never sent to the browser, lazy-initialized, RLS-with-no-policies as defense in depth) — but since it is wholly unused by any route today, this is a design intention, not yet an exercised security control.

### 12.1 Glossary (terms pulled directly from `SPEC.md` and the codebase)

| Term | Meaning |
|---|---|
| **Reefer** | A refrigerated shipping container; the core unit the whole app tracks. |
| **Gate-in** | The event of a container formally entering the yard/depot and becoming active in the pipeline. |
| **Readiness** | The overall state of "is this container's checklist/sections complete and cleared for release" — computed by `isReady()` (v1) / `readyAt` (v2). |
| **Survey** | (v2) The pre-gate-in physical/mechanical inspection that determines which Sections a container needs. Outcome: `ready` or `needs-work`. |
| **PTI (Pre-Trip Inspection)** | A section/stage (both v1 and v2) covering lights, strip & curtain, mantrap, and (v1) pull-down temperature/door-seal/recorder checks before release. |
| **Repairment** | (v2) The display name for the stage where body/structural repair tasks generated from a flagged Survey item are done — same underlying `all_rounder` `SectionKind` as the All-Rounder worker type, but named for the work, not the worker (`SPEC.md` §8 item 27). |
| **All-Rounder** | (v2) A worker type who staffs the Repairment stage and ad hoc tasks (lights/strip/curtain install, dry/reefer repair, painting, logo, or "Other" with a required free-text reason). |
| **Anteroom** | (v1/v2) A reefer configuration variant with an airlock/mantrap compartment, adding electrical/mantrap checklist items; has `internal`/`external` sub-variants. |
| **Double (compressor)** | A container type with two compressors, adding mechanical checklist/day-budget work. |
| **IICL grade (A–D)** | Institute of International Container Lessors condition grading used for off-lease returning units (`GRADES`/`GRADE_LABELS` in `process.ts`). |
| **Stage budget** | The planned number of working days a container type is allotted in a given v1 pipeline stage; exceeding it marks the container "late." |
| **Off-lease unit** | A container expected back from a customer, not yet gated in — lets the depot plan repair capacity ahead of physical arrival. |
| **Ready to Move** | (v2) The gate equivalent to v1's `isReady` — every section Survey flagged is fully complete (every task's timer stopped or marked N/A). |
| **Movement log** | (v2) A separate append-only record of physical container movement events (load/offload/shift), distinct from the section/task checklist model. |
| **Worker (record)** | (v2) A non-authenticated person record (Painter, Painter Helper, Technician, All-Rounder, Cleaner, Tea Boy, Sailing Crew) that Admin creates/assigns/edits — not a login. |
| **Admin / Owner** | (v2 roles) Admin: the single authenticated operator with full control. Owner: a planned future read-only role, not yet built. |

### 12.3 Key config files explained

- **Root `package.json`** — npm workspaces (`packages/*`, `apps/*`). Key scripts: `setup` (env init + token generation + db push + seed), `dev` (concurrently runs API on :4000 and web on :5173), `verify` (typecheck + eslint + stylelint + unit tests — the only automated gate that exists, and it is developer-run, not CI-run).
- **`apps/api/prisma/schema.prisma`** — SQLite datasource; models `User`, `Depot`, `Technician`, `Container`, `ContainerTask`, `ContainerEvent`, `OffLeaseUnit`, `CustomerOrder`. Header comment explicitly notes a future Postgres swap was anticipated from the start.
- **`apps/api/supabase/config.toml`** — standard Supabase CLI local-dev config (API port 54321, DB port 54322); not evidence of a provisioned cloud project, only of local tooling being set up.
- **`.stylelintrc.json`** — extends `stylelint-config-standard`; hard-bans hex colors and `rgb()/hsl()`/named colors outside the two gitignored generated files (`tokens.css`, `crystal.css`), forcing every color through a design-system `var(--token)`.
- **`eslint.config.js`** — flat config (`typescript-eslint` + `jsx-a11y` + `react-hooks`), ignores `generated/**`, `prisma/**`, `source/**`. `no-unused-vars` and `eqeqeq` enforced as errors.
- **`apps/api/.env.example`** — documents every required/optional env var (see §9); the only file telling an operator what secrets to supply.
